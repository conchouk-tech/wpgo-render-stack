# WPGo Release Operations

This runbook defines how a WPGo commercial release should move from release candidate to production and how to roll back safely.

## Release principles

- Production releases come from reviewed release branches/PRs, not local developer machines.
- CI produces the WordPress package and checksum.
- Release metadata is signed by the control plane.
- Published package bytes must match the SHA-256 in the signed manifest.
- Production database/state migrations must be backwards-compatible wherever practical.
- Do not change the production MCP secret during an ordinary deploy.
- Existing AI connections are a release-critical compatibility surface.

## Pre-release gate

Before candidate promotion verify:

- `GA-READINESS.md` status;
- full RC workflow green;
- dependency security workflow green;
- billing integration workflow green;
- renderer integration workflow green;
- WordPress RC package/checksum generated by CI;
- release notes complete;
- production config/secrets present;
- backup/restore point available;
- rollback package/version identified;
- support/incident owner available during release window.

## WordPress package flow

1. CI builds the package from the tagged/reviewed source.
2. CI computes SHA-256.
3. Package is uploaded to controlled HTTPS distribution storage.
4. Production control-plane release variables are set to version, package name, SHA-256 and HTTPS URL.
5. Manifest is signed by the control plane.
6. Independent verification fetches public key + manifest, validates Ed25519 signature and checks expected metadata.
7. Download package and verify SHA-256 again from distribution location.
8. Test update on a disposable/representative WordPress site before broad release.

## Service deploy order

For backwards-compatible changes, prefer:

1. persistent data/state infrastructure readiness;
2. commercial API migrations/startup;
3. control plane;
4. MCP gateway;
5. portal;
6. renderer;
7. WordPress package/update manifest.

For changes that require a different order, document the compatibility reason in the release PR.

## MCP deploy rules

A normal deploy must preserve:

- public MCP origin;
- `WPGO_MCP_SECRET`;
- persistent shared OAuth/connection state;
- resource/site-token validation behavior;
- supported OAuth metadata endpoints;
- refresh-token compatibility.

After deploy, verify an existing pre-deploy connected client can use or refresh its connection without reauthorization.

## Database migrations

Runtime migrations in application startup must be idempotent. Destructive schema changes require an explicit migration/backup plan and should not be embedded casually in normal startup.

Before a destructive migration:

- backup;
- test migration on a copy;
- document rollback/forward fix;
- confirm expected application compatibility.

## Canary / staged rollout

Preferred commercial rollout:

1. internal/test sites;
2. private beta customers;
3. small commercial beta cohort;
4. broader release after telemetry/support stability;
5. GA.

If infrastructure/provider features permit traffic splitting/canaries later, add them without changing the core release principles.

## Rollback triggers

Rollback or disable the affected feature when there is:

- OAuth refresh/reconnect regression;
- cross-site/resource binding failure;
- write-approval bypass or incorrect destructive action;
- widespread 5xx/connection failure;
- billing lifecycle corruption;
- invalid update signature/hash behavior;
- database integrity regression;
- renderer network-policy regression.

## Rollback procedure

1. Stop further rollout/update publication.
2. Preserve logs/request IDs/deploy event details.
3. If the WordPress package is affected, repoint the signed update manifest only through the documented safe release process; do not silently overwrite an artifact under the same immutable version.
4. Redeploy the previous known-good service commit/config without rotating stable production secrets.
5. Verify health and existing AI connection refresh.
6. Reconcile any billing/data mutations caused during the affected window.
7. Add a regression test before re-releasing the fix.

## Versioning

Use SemVer-like product versions:

- `4.5.0-rc.N` for release candidates;
- `4.5.0` for GA;
- patch releases for compatible bug/security fixes;
- minor versions for compatible feature releases;
- major version only for intentional breaking customer/API behavior.

Individual backend component versions may differ but must be listed in the product release notes.

## Release record

For each production release retain:

- product/component versions;
- source commit/tag;
- CI run IDs;
- package SHA-256;
- signed manifest snapshot/reference;
- release timestamp;
- production deploy IDs;
- migration notes;
- known issues;
- rollback version;
- approval/reviewer identity.
